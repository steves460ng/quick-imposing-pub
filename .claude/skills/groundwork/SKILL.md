# 프로젝트 초기 설정

목표: 빈 저장소(또는 거의 빈 저장소)에 **Claude Code와 함께 쓰기 좋은 프로젝트 기본 세팅**(CI, 검사 명령, 작업 규칙)을 한 번에 깐다.
1순위는 CI와 일관된 검사라는 기본기이고, 토큰 절감은 그 구조에서 따라오는 부수 효과다. 사용자에게 설명할 때도 이 순서를 지키고, 절감 효과를 단정하지 않는다.

원칙:
- 결정적인 작업(lint, 테스트, 빌드, 포맷, 구조 요약)은 스크립트와 CI가 맡고, Claude는 판단이 필요한 일만 한다.
- CLAUDE.md에 부탁하는 것으로 끝내지 않는다. 막을 수 있는 것은 권한과 훅으로 **강제**한다.
- CI 결과는 사용자가 옮겨 주지 않아도 Claude가 **짧게 회수**할 수 있게 한다. 회수 수단은 환경마다 다르므로 실제로 동작하는 것을 확인해서 쓴다.
- 세션을 어떻게 나눌지는 사용자의 작업 방식을 따른다. 규칙으로 강제하지 않는다.
- 저장소에 이미 있는 관습(인수인계 문서, 테스트 실행 방식, 포맷 정책)이 있으면 그것을 우선한다.

이 스킬은 오래 쓸 프로젝트에 맞다. 며칠 쓰고 버릴 실험용 저장소라면 세팅 비용이 절감액보다 클 수 있으니, 시작 전에 한 줄로 알린다.

## 0. 사전 확인

- `git status`와 파일 목록으로 저장소 상태를 확인한다.
- 템플릿 저장소에서 만든 저장소인지 확인한다. `.template/MANIFEST`가 있으면 거기 적힌 파일은 템플릿 전용 파일이므로 기존 파일로 보지 않고, 충돌로 묻지도 않는다. 이 파일들은 4단계에서 정리한다.
- 그 밖의 파일이 이미 있으면 덮어쓰지 않는다. 무엇이 있는지 보고하고, 겹치는 파일은 사용자에게 처리 방법을 묻는다.
- **이미 코드가 있는 저장소**라면 인터뷰 전에 적용 검토부터 한다. 2단계 생성물마다 "그대로 넣을 것 / 고쳐서 넣을 것 / 넣지 않을 것"으로 나눠 이유와 함께 보고하고, 사용자가 고른 것만 만든다. 특히 아래를 확인한다.
  - 인수인계 문서(HANDOFF, PR 설명 등)가 이미 있는가 → 있으면 작업 노트를 새로 만들지 않는다
  - 포맷 도구가 없는가 → 새로 넣으면 첫 적용 때 코드 전체가 바뀌므로, 포맷 훅은 기본으로 넣지 않고 사용자에게 묻는다
  - 기존 테스트 실행 방식이 있는가 → 그 명령을 막는 훅은 넣지 않는다
  - 테스트 생성 도구(2-10)를 어디까지 남길지 3번 질문과 같은 선택지로 묻는다
  - 큰 바이너리나 샘플 파일이 있는가 → 읽기 차단 대상에 넣는다
- 기본 브랜치를 확인하고 작업 브랜치 `setup/initial`을 만든다.

## 1. 인터뷰

진행 규칙:
- 한 번에 질문 하나만 한다. AskUserQuestion을 쓸 수 있으면 쓴다.
- 선택지마다 추천 기본값을 첫 번째에 "(추천)"으로 둔다.
- 앞선 답에서 이미 알 수 있는 질문은 건너뛴다.
- 사용자가 "알아서"라고 하면 추천값으로 정하고 넘어간다.
- 사용자가 "다시 앞 질문으로"라고 하면 바로 앞 질문을 다시 묻는다.
- 질문은 아래 7개를 넘기지 않는다.

질문:
1. 프로젝트 한 줄 설명과 종류 (웹앱 / API 서버 / CLI / 라이브러리 / 기타)
2. 언어와 프레임워크
3. 패키지 매니저, 테스트·lint·포맷 도구 (스택 관습에 맞는 기본값을 제시). 이어서 테스트 생성 도구(2-10)를 묻는다: 명령으로만 쓰기 (추천) / 자동 제안까지 / 넣지 않기
4. CI 실행 시점: PR + main push (추천) / 모든 push / PR만
5. 배포: 지금은 없음 (추천) / 대상 지정
6. CONTEXT.md: 파일이 수십 개 이상으로 커질 프로젝트면 "예", 작은 프로젝트면 "아니오"를 추천한다
7. 지켜야 할 코딩 규칙이나 금지 사항 (없으면 건너뜀)

끝나면 결정 사항을 짧은 표로 보여 주고 "이대로 만들까요?" 하고 한 번만 확인한다.

## 2. 생성물

인터뷰에서 정하지 않은 도구나 의존성은 추가하지 않는다. 최소 구성으로 만든다.
스크립트는 스택 언어나 POSIX sh로 쓴다. 추가 의존성이 필요한 언어는 쓰지 않는다.

### 2-1. 프로젝트 골격
스택 초기화와 최소 소스 파일, 그리고 검사가 실제로 돌도록 샘플 테스트 1개를 만든다.

### 2-2. 조용한 검사 명령
스택 관습에 맞는 이름으로 만든다 (`npm run check`, `make check`, `scripts/check` 등).
- 순서: (CONTEXT.md를 쓰면) CONTEXT.md 갱신 → 포맷 검사 → lint → 타입 체크(해당 시) → 테스트
- 성공하면 한 줄만 출력한다.
- 실패하면 실패 항목, 에러 한 줄, `파일:라인`만 출력한다. 전체 로그는 출력하지 않는다. 실패 항목이 많으면 앞의 20개만 보여 주고 나머지는 개수만 적는다.
- 경로를 인자로 받으면 그 경로와 관련된 테스트만 실행한다.
- `--ci` 옵션을 주면 CONTEXT.md를 갱신하는 대신, 최신 상태인지 확인만 하고 다르면 실패한다.

### 2-3. CI 결과 확인 방법
환경마다 쓸 수 있는 수단이 다르다. 어떤 환경에서는 `gh api`로 Actions를 조회할 수 있고, 어떤 환경에서는 `gh`를 검색에만 쓸 수 있으며 CI 결과는 GitHub MCP 도구로만 확인할 수 있다. 만들기 전에 아래 순서로 실제로 확인하고, 처음으로 동작하는 수단 하나만 쓴다.

1. **GitHub MCP 도구**: 세션에 워크플로 실행이나 체크 결과를 읽는 GitHub MCP 도구가 있으면 그것을 쓴다. 스크립트는 만들지 않고, CLAUDE.md에 "CI 결과는 GitHub MCP 도구로 확인하고, 실패한 단계의 출력만 본다"는 규칙만 적는다.
2. **`gh api`**: MCP 도구가 없을 때, `gh api repos/{owner}/{repo}/actions/runs?per_page=1`가 실제로 응답하면 아래 `ci-status` 명령을 만든다.
3. **둘 다 안 됨**: 스크립트를 만들지 않는다. CLAUDE.md에 "CI가 실패하면 사용자에게 Job summary 몇 줄을 요청한다"고 적는다.

`ci-status` 명령 (2번일 때만): 스택 관습에 맞는 이름으로 만든다 (`npm run ci-status`, `scripts/ci-status` 등).
- `gh api`(REST)만 쓴다. GraphQL을 쓰는 `gh` 하위 명령은 환경에 따라 막힐 수 있다.
- 현재 브랜치의 가장 최근 워크플로 실행 1건을 조회한다.
- 진행 중이면 상태 한 줄만 출력한다. 성공하면 한 줄만 출력한다.
- 실패하면 실패한 job의 로그를 받아, 검사 명령 단계의 출력만 잘라 최대 40줄까지 보여 준다. CI도 조용한 검사 명령을 그대로 돌리므로 이 부분은 원래 짧다.
- `gh`가 없거나 인증이 안 되면 "CI 결과를 가져올 수 없음. Actions 탭의 Job summary를 붙여 달라"는 한 줄을 출력하고 종료한다.

### 2-4. CONTEXT.md 생성 스크립트 (6번 질문이 "예"일 때만)
LLM 없이 결정적으로 만든다. 스크립트로 정확히 뽑을 수 있는 것만 담는다.
- 디렉터리 구조 (생성물, 의존성 폴더 제외, 깊이 제한)
- 진입점과 실행 명령
- 내보내는 모듈·함수 이름 목록 (스택 도구로 뽑을 수 있을 때만)

모듈의 "역할" 같은 해석은 넣지 않는다. 그건 스크립트로 만들 수 없다.
main에 자동 커밋하는 워크플로는 만들지 않는다. 갱신은 검사 명령이 하고, CI는 최신 상태인지 확인만 한다.

### 2-5. 작업 노트 `.claude/notes.md` (인수인계 수단이 없을 때만)
세션이 바뀌어도 작업을 이어 갈 수 있게 하는 파일이다. 저장소에 이미 HANDOFF 문서, 작업 일지, PR 설명 같은 인수인계 수단이 있으면 만들지 않고 그것을 쓴다. 기록이 두 군데로 나뉘면 오히려 헷갈린다.
새로 만들 때는 아래 틀만 둔다.

```
# 작업 노트 (20줄 이하, 매번 덮어쓴다)
## 현재 상태
## 다음 할 일
## 주의할 점
```

### 2-6. `.claude/settings.json` (권한과 훅)
Claude Code 공식 설정 형식을 따른다.
- **권한 차단** (`permissions.deny`): lock 파일, 빌드 산출물, 의존성 폴더, 생성 코드를 `Read`로 읽지 못하게 한다. 스택에 맞는 경로만 넣는다.
- **PreToolUse 훅** (`Bash` 대상): `.claude/hooks/` 아래 스크립트로 만든다. 표준 입력의 JSON에서 실행하려는 명령을 읽고, 다음 경우에 종료 코드 2로 막으면서 대신 쓸 명령을 stderr에 한 줄로 알린다.
  - 테스트 러너, linter를 검사 명령 없이 직접 실행할 때 → 검사 명령을 쓰라고 안내
  - `cat`, `head`, `tail` 등으로 차단 대상 파일을 읽을 때 → 읽지 말라고 안내
  - `git push`로 기본 브랜치에 직접 push할 때 → 작업 브랜치에서 PR로 합치라고 안내

  그 밖의 명령은 그대로 통과시킨다. 너무 넓게 막지 않는다.
- **병합 확인** (`permissions.ask`): PR 병합 수단을 넣어 병합할 때마다 사용자 확인을 받게 한다. 세션에서 쓸 수 있는 것만 넣는다 (`mcp__github__merge_pull_request`, `Bash(gh pr merge:*)` 등). 막는 것이 목적이 아니라 승인을 받는 것이 목적이므로 `deny`가 아니라 `ask`에 넣는다.
- **PostToolUse 훅** (`Edit`, `Write` 대상): 포맷 도구가 있거나 인터뷰에서 넣기로 했을 때만 만든다. 수정된 파일에 포맷 도구를 돌리고, 성공하면 아무것도 출력하지 않는다.
- 훅 스크립트 경로는 `$CLAUDE_PROJECT_DIR` 기준으로 적는다.

### 2-7. CLAUDE.md (60줄 이하)
- 프로젝트 개요 2~3줄
- 세션 규칙 (권장 사항으로 적고, 강제하지 않는다)
  - 세션을 시작할 때 인수인계 문서(notes.md 또는 기존 HANDOFF 등)가 있으면 먼저 읽는다. CONTEXT.md가 있으면 그다음에 읽는다. 저장소 전체 탐색은 필요할 때만 한다
  - 작업이 일단락되면 인수인계 문서를 짧게 갱신한다
- 검사 규칙
  - 검사는 검사 명령만 쓴다. 바뀐 부분과 관련된 경로만 넘긴다. 전체 테스트는 CI가 한다
  - push한 뒤에는 2-3에서 정한 방법으로 CI 결과를 확인한다. 진행 중이면 잠시 기다렸다가 최대 3번까지만 다시 확인하고, 그래도 끝나지 않으면 사용자에게 넘긴다
- 브랜치 규칙
  - 기본 브랜치에 직접 push하지 않는다. 변경은 작업 브랜치에서 하고 PR로 합친다. 브랜치 이름 형식은 정하지 않는다
  - PR 병합은 사용자가 대화에서 해당 PR을 명시적으로 승인했을 때만 한다. 리뷰 승인, CI 통과, 다른 PR에 대한 이전 승인은 허가가 아니다
- 포맷 훅이 있으면 포맷은 훅에 맡긴다. 직접 지적하거나 고치지 않는다
- 권한으로 막힌 파일을 우회해서 읽지 않는다
- 인터뷰에서 받은 코딩 규칙

### 2-8. `.github/workflows/ci.yml`
- 트리거는 인터뷰 결과를 따른다
- `paths-ignore`로 문서만 바뀐 변경(`**/*.md`, `docs/**`)은 건너뛴다. 단, CONTEXT.md를 쓰는 프로젝트라면 CONTEXT.md는 이 무시 목록에서 뺀다
- 의존성 캐시를 쓴다
- 검사 명령을 `--ci` 옵션으로 실행한다
- 실패하면 요약을 `$GITHUB_STEP_SUMMARY`에도 남긴다

### 2-9. 기타
`.gitignore`, 포맷 도구 설정 파일.

### 2-10. 테스트 생성 도구
템플릿에 들어 있는 `.claude/skills/auto-test/`, `.claude/commands/generate-tests.md`, `.claude/agents/test-writer.md`를 3번 질문의 답에 따라 정리한다.
- 명령으로만 쓰기: `auto-test` 스킬 폴더를 삭제한다. 사용자가 `/generate-tests`를 부를 때만 동작한다.
- 자동 제안까지: 세 파일을 모두 남긴다. `auto-test`는 테스트 없는 새 소스 파일이 생겼을 때만 한 번 제안한다.
- 넣지 않기: 세 파일을 모두 삭제한다.

파일을 남기면 `generate-tests.md` 7단계 `Check command:` 줄의 `none`을 2-2에서 만든 검사 명령으로 바꾸고, frontmatter `allowed-tools`에 그 검사 명령 하나만 `Bash(<검사 명령>:*)` 형태로 추가한다. 이렇게 해서 test-writer가 쓴 테스트를 메인 세션이 검사 명령으로 실행해 확인한다. test-writer에는 Bash를 주지 않는다.
`.claude/THIRD_PARTY_NOTICES.md`는 남긴 파일이 있으면 그대로 두고, 세 파일을 모두 지웠으면 test-generator 항목을 지운다.

## 3. 검증

- 검사 명령을 실행해 통과하는지 확인한다. 실패하면 고친 뒤 다시 실행한다.
- 검사 명령에 일부러 실패를 하나 만들어, 출력이 짧게 나오는지 확인한 뒤 되돌린다.
- `.claude/settings.json`이 올바른 JSON인지 확인한다.
- PreToolUse 훅에 샘플 JSON을 넣어 막아야 할 명령은 종료 코드 2로 막고, 일반 명령은 통과시키는지 확인한다. 막아야 할 명령 샘플에는 기본 브랜치로의 `git push`(예: `git push origin main`)를 포함하고, 작업 브랜치 push는 통과하는지도 확인한다.
- CONTEXT.md를 쓰면 생성 스크립트를 실행해 만든다.
- 테스트 생성 도구를 남겼으면 `generate-tests.md`의 검사 명령이 `none`이 아니라 실제 명령으로 바뀌었는지 확인한다.
- `actionlint`를 쓸 수 있으면 워크플로 파일을 검사한다. 없으면 YAML 문법만 확인한다.

## 4. 커밋과 PR

- 템플릿에서 만든 저장소라면 커밋 전에 템플릿 전용 파일을 정리한다. `.template/MANIFEST`의 `delete` 항목은 삭제하고, `replace` 항목은 이 프로젝트용으로 새로 쓴다. README.md는 새 프로젝트 설명으로, CLAUDE.md는 2-7에서 만든 내용으로 바꾼다. `.claude/skills/groundwork/`는 재실행용으로 남긴다.
- 커밋하고 `setup/initial` 브랜치를 푸시한 뒤 PR을 만든다.
- 워크플로 파일 때문에 푸시가 거부되면 GitHub 권한 문제라고 알린다. 사용자가 GitHub 앱 권한을 확인하거나 워크플로 파일만 직접 추가하도록 안내한다.
- 푸시한 뒤 2-3에서 정한 방법으로 CI 결과를 실제로 한 번 가져와 본다. 안 되면 그 사실을 보고에 적는다.

## 5. 마무리 보고

짧게 보고한다.
- 만든 파일 목록 (파일마다 한 줄 설명)
- CI 결과 확인 수단으로 무엇을 골랐고(MCP / `ci-status` / 사용자 요청), 실제로 동작했는지
- 테스트 생성 도구를 어떻게 정리했는지 (명령으로만 / 자동 제안까지 / 넣지 않기)
- 사용자가 직접 할 일 체크리스트:
  - PR 확인 후 머지
  - 필요한 시크릿 등록 (있을 때만, 이름 명시)
  - 웹 Claude Code 클라우드 환경 설정 스크립트에 넣을 의존성 설치 명령 (텍스트로 제공)
  - (선택) GitHub 저장소 설정에서 기본 브랜치 보호 규칙 켜기: 직접 push 금지, PR 필수. 저장소 관리자만 설정할 수 있고, 비공개 저장소는 요금제에 따라 쓸 수 없을 수 있다
- 효과 확인 방법 한 줄: 처음 몇 번은 비슷한 작업을 이 저장소와 다른 저장소에서 해 보고 사용량을 비교해, 효과 없는 장치는 빼라고 권한다.

## 재실행할 때

이미 설정된 저장소에서 다시 실행하면 인터뷰는 바뀐 항목만 묻는다. 기존 파일은 덮어쓰지 않고 변경할 내용을 diff로 보여 준 뒤 확인을 받고 갱신한다.
